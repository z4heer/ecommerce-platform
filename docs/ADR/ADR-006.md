# ADR-006: Enterprise Page Header Component

## Status

Accepted

---

## Date

2026-06-30

---

## Context

As the Enterprise E-Commerce Platform grows, multiple feature modules require a consistent page header.

Examples include:

* Dashboard
* Products
* Product Details
* Orders
* Customers
* Reports
* Administration

Without a reusable component, each feature would implement its own title, subtitle, spacing, divider, and action area, resulting in duplicated code, inconsistent user experience, and increased maintenance effort.

The project follows a reusable Enterprise Design System architecture where common UI elements are implemented once and shared across all modules.

---

## Problem Statement

Individual feature pages require a consistent mechanism to display:

* Page title
* Optional subtitle
* Contextual actions
* Future breadcrumb integration

Implementing these independently within each feature would:

* Duplicate HTML and SCSS
* Produce inconsistent layouts
* Increase maintenance effort
* Make future design updates expensive

---

## Decision

Introduce a reusable standalone Angular component named **PageHeaderComponent** as part of the Enterprise Design System.

The component will:

* Render a page title (required)
* Render an optional subtitle
* Render an optional divider
* Support projected action buttons using Angular content projection
* Remain presentation-only with no business logic
* Be reusable across all authenticated modules

The component uses:

* Angular 19 Standalone Components
* Angular Signal Inputs (`input()`)
* `ChangeDetectionStrategy.OnPush`
* Semantic HTML (`<header>`, `<h1>`)
* Angular Material Divider
* Responsive Flexbox layout

---

## Architecture

```
PageContainer
        │
        ▼
PageHeader
        │
 ├── Title
 ├── Subtitle
 ├── Action Slot
 └── Optional Divider
```

Feature pages compose the layout as follows:

```
PageContainer
        │
        ▼
PageHeader
        │
        ▼
Feature Content
```

---

## Alternatives Considered

### Option 1 – Duplicate header markup in every feature

**Rejected**

Reasons:

* High code duplication
* Inconsistent spacing
* Difficult maintenance
* Poor scalability

---

### Option 2 – Pass action buttons through Inputs

**Rejected**

Reasons:

* Limited flexibility
* Difficult to support multiple actions
* Increased component complexity

---

### Option 3 – Use Angular Content Projection

**Accepted**

Reasons:

* Maximum flexibility
* Clean separation of concerns
* Supports any number of projected actions
* Aligns with Angular component composition best practices

---

## Consequences

### Positive

* Consistent page layout across the application
* Reduced HTML duplication
* Easier maintenance
* Improved developer productivity
* Better scalability
* Supports future breadcrumb integration
* Simplifies feature development

### Negative

* Introduces one additional reusable component to maintain
* Requires developers to understand content projection

---

## Implementation Decisions

The component follows these architectural principles:

* Single Responsibility Principle (SRP)
* SOLID design principles
* DRY (Don't Repeat Yourself)
* KISS (Keep It Simple)
* Presentation-only component
* No business logic
* No HTTP communication
* No services
* No routing dependencies

---

## Performance Considerations

The component is optimized using:

* `ChangeDetectionStrategy.OnPush`
* Angular Signal Inputs
* No RxJS subscriptions
* No unnecessary DOM rendering
* Minimal template logic

---

## Accessibility

The component follows accessibility best practices:

* Semantic `<header>` element
* Proper `<h1>` heading hierarchy
* Keyboard-accessible projected action buttons
* Responsive layout without loss of usability

---

## Future Enhancements

The following enhancements are planned without changing the component's public API:

* Breadcrumb projection area
* Dynamic page icons
* Page metadata support
* Theme token integration
* Internationalization (i18n)
* Role-aware action visibility
